# KinShip: build reference for steps 12 to 17 (moved out of the handoff on 2026-11-21)

The build-status note (`kinship-build-status-and-handoff.md`) is the current state. This file keeps the detailed descriptions of four finished 0.2 features that the handoff used to carry in full: invitations and passwords, the first-run wizard, backups and the safety copy, and Admin -> Updates. Nothing here is a rule that the handoff does not summarise; where they differ, the handoff wins. Read it when you work on one of these areas.

## Reference
- Invitations and passwords (ADR 0012, migration 0011): `account_links` (kind `invite` or `reset`; only the SHA-256 of the token is stored; single use; revoke; regenerate replaces the token in the same row; RLS enabled but not forced, no policies and no grants for the app role, so all access is through SECURITY DEFINER functions that check the caller's role). Invitations last 7 days; admin set-password links last 24 hours. One open invitation per lowercased email and per person; one open set-password link per account. **Who may do what:** SuperAdmin invites Family Admin, Member and User; Family Admin invites Member and User; nobody invites a second SuperAdmin; set-password links: a Family Admin for Members and Users only, the SuperAdmin for anyone except themselves (a locked-out SuperAdmin uses the CLI). An invitation may name an existing person with no account (a Member with no person is read-only; the dialog warns). Links are `/invite#<token>` and `/reset#<token>`: the fragment never reaches nginx or a Referer, the page strips it with `history.replaceState`, and the token travels only in POST bodies (checked in a real web image: nginx log token count 0). Links are shown once (closing the dialog loses it; "make a new link" regenerates). Every bad link (unknown, expired, used, revoked) gives the identical 404 `invalid_link`. Limits: link routes 20 failures per IP and 200 global per 15 minutes; password change 10 per account and 20 per IP. `POST /api/auth/password` deletes the account's other sessions and rotates the current token; a self change or the CLI retires any open set-password link for that account. `users` also has `last_sign_in_at`, `password_changed_at` and `password_changed_via` (`setup`, `self`, `admin_link`, `cli`, `invitation`; null means not recorded, for old accounts); the Account card shows "Password last changed ... using ..." so an owner can see an admin link did it (from 0.6 an account's private medical record is readable by whoever controls the account). Admins read all `users` rows through `users_select_admin` (the hash has no column grant). Email is unique ignoring case (`lower(email)` index).
- First-run wizard (ADR 0013, migration 0012): seven steps (Account, Tree, You, Partner, Parents, Children, Review). **Nothing is written until Review**: the wizard keeps everything in memory (no localStorage or sessionStorage except the color-scheme mirror), a refresh restarts it, and `POST /api/setup` creates the account, tree, people and relationships in one transaction through `kinship_auth.complete_setup_family` (advisory lock plus a "no users" re-check, so exactly one concurrent finish wins; any failure rolls back everything). The token is typed in step 1 and checked early by `POST /api/setup/check` (204 or 403 `invalid_setup_token`, sharing the setup failure limiters), then sent again with the final post. Every setup error carries a `field` path (`family.children.1.birth`) that the web maps back to a step and field. Skip is allowed on Partner, Parents and Children, not on You; gender is optional everywhere ("Not specified" is null); the partner has Living or Deceased (Widowed requires Deceased; Married plus Deceased becomes Widowed automatically); when both parents are entered a "their relationship" select (default Married) sets their union; children choose the partner or "Not on the tree" (hidden with no partner; cap 30); all links are birth links. Warnings (`parent_too_young`, same name and birth date) are soft and not stored. Setup lands on `/tree/{you}`. The legacy `person` field still works for scripted installs but cannot be combined with `family`. Migration 0012 dropped the 5-argument `complete_setup` (#9); the 7-argument one stays until a later contract step.
- Backups and the safety copy (ADR 0014, migration 0013; PRs #66 to #72): **the api keeps the owner credentials for maintenance jobs** (amends ADR 0001; they are removed from `process.env` after config load, passed only in a child process's explicit environment, never in argv or logs; `/proc/<pid>/environ` still holds them, as the ADR says). A dump runs `pg_dump -Fc --no-owner` as the OWNER role in a short-lived child (the image has `postgresql18-client`, +9 MB, PostgreSQL License), only if the owner has `rolsuper` or `rolbypassrls`; otherwise a backup refuses with the exact `ALTER ROLE ... BYPASSRLS` fix (in INSTALL.md) and the pre-migration safety copy is SKIPPED with a recorded reason (so those installs can still upgrade); a real dump failure on a capable owner blocks the migration. Archive `kinship-YYYY-MM-DD-HHMM.tar.enc` (UTC; `-2` suffix inside one minute): tar of `manifest.json`, `database.dump`, `files/` (slot only; no media exists yet); authenticated cleartext header (format, app version, schema number, KDF parameters); scrypt (N=2^17, r=8, p=1) plus HKDF, AES-256-GCM in 64 KiB chunks with a final-chunk flag in the AAD; a wrong passphrase is told apart from corruption or truncation before any restore step. Manifest has per-table counts and digests under one snapshot and an RLS and grants fingerprint (one SQL query, also run inside the restore transaction). `BACKUP_PASSPHRASE` (or `_FILE`), 16 characters minimum, `change-me-backup` refused; `BACKUP_ENABLED=on` is the master switch for the schedule only; `BACKUP_DEST` accepts only `local` (s3 is 1.1). Recovery without KinShip: standalone `kinship-decrypt.mjs`, the format spec in `docs/`, `kinship backup-decrypt` (plain openssl cannot decrypt chunked GCM). **Restore is in the CLI (`docker compose stop web api`, then `docker compose run --rm api kinship restore <file>`) and, since step 36 (ADR 0031), in Admin -> Backups; the in-app restore, its maintenance mode and its refusals are described in `kinship-build-status-and-handoff.md` (Repo section). The CLI path:** preflight (full verify in a work folder on the backups volume, refuse newer schema, newer Postgres major, role-name mismatch, open app-role connections, low disk), typed `RESTORE`, a `pre-restore-<ts>` safety dump, `ensureAppRole` first (so it works on a brand-new empty Postgres), then one explicit `BEGIN ... COMMIT` script (drop and recreate schemas, restore, verify counts against the manifest, delete all sessions, revoke open `account_links`), then migrations if the backup is older, then an `upgrade_log` row. The CLI executes only authenticated archives, never plain `.sql.gz` copies (manual psql steps are documented). "Test the latest backup" restores into `kinship_verify_<hash of db name>_<random>` as the owner (degrades to decrypt, tag and manifest checks without CREATEDB), compares counts, digests, fingerprint and migration checksums, runs a functional check as the app role, and always drops the database (plus a startup sweep). Scheduler: a 60-second tick in the api, catch-up two minutes after start, Postgres advisory lock plus a lock file, temp file then rename, mode 0600 (folder 0700), free-space check, retention daily/weekly/monthly 7/4/6 by default (only our file names; the newest good archive is never deleted; `pre-upgrade-*` and `pre-restore-*` keep 3 each), history in `state.json` on the volume (written atomically; a restore cannot rewind it). **Safety copy before migrations (on by default; `app_settings` key `safety_copy`, read safely when the table does not exist yet):** dumps before any pending migration on a database that already has applied ones, verified by reopening, named by schema numbers (`pre-upgrade-0012-to-0013`), `.tar.enc` in the same archive format when a passphrase is set, otherwise plain `.sql.gz` mode 0600 with a warning. Break-glass: one-shot `KINSHIP_SAFETY_COPY=skip` (only that value; documented in INSTALL and UPGRADE troubleshooting, logged and recorded). Tables: `app_settings` (SuperAdmin-only RLS, allow-listed keys with shared parsers; step 17 adds the update-check toggle) and `upgrade_log` (event migrate or restore, from and to schema number and version, the safety-copy file name or `safety_note`). Migration 0013 also fixed #35 (the three owner-only widow policies now test membership of the table owner, not a hardcoded role name). Backups folder: bind mount `./data/backups:/var/lib/kinship/backups`; Linux needs `mkdir -p data/backups && sudo chown 1000:1000 data/backups` (the api checks and prints the command, and for an unmounted folder prints the exact compose lines); compose healthcheck `start_period` is 600s so a long safety copy is not reported unhealthy; `scripts/smoke-test.sh` creates `data/backups` first. Routes (SuperAdmin only, `requireSuperAdmin`, `BACKUP_ROUTES` in `packages/shared`): list and status, run now (202, poll), test, settings get and patch, download ticket, download. Download re-asks the password and returns a single-use 30-second ticket bound to session and file; plain safety copies are listed but never offered for download. `ensureAppRole` now runs under the migration lock and changes only the password unless role attributes are unsafe.
- Updates (ADR 0015, migration 0014; PRs #75 to #83): Admin -> Updates (SuperAdmin; a Family Admin sees the tab with a note only). The daily check runs in a small shared job runner (built in step 17; the backup scheduler and the 0.4 birthdays job can use it): conditional requests (ETag), allow-listed redirects, size and time limits, back-off, rate-limited Check now, `HTTPS_PROXY` honored (tested against a local proxy), nothing sent when the switch is off, no data about the install sent. The toggle is `app_settings` key `updates.check` (in-app, default on; there is no environment variable); Include pre-releases (off) and the safety-copy switch (`safety_copy`) sit next to it. The scheduled check rereads the next-check time from the database when due; turning the switch on makes the next tick check at once. Each GitHub release carries a `release-manifest.json` made by the pipeline (generator, validator and dry-run artifact built in step 17; a stable release is compared with the latest earlier tag of any kind; the CHANGELOG heading reader accepts the Keep a Changelog and release-please forms; `upgradeFrom` is always null). The app offers every stable release newer than the running version and combines the flags. Migration 0014 adds `update_check`, four per-account columns (last seen version, banner and backup-gate memory) with a trigger so new accounts start current, and `upgrade_log.backup_version`; a restore logs the version that was running before. Seven SuperAdmin routes plus `GET /api/updates/whats-new?latest=1` for the About button. Web: Updates tab, banner on Admin pages, "What's changing" popup (each release's own Markdown, not regrouped; backup warning and the soft gate with the "I have a backup I can restore" tick), "What's new" popup for every admin after an update (regrouped from the bundled CHANGELOG; migration note and safety copy name from `upgrade_log`; downgrade notice), About page with a What's new button. Markdown from the internet is rendered by an own inert renderer (no raw HTML, no new dependency; scans capped at 2,000 characters after CI caught a quadratic case). The api image now carries CHANGELOG.md and UPGRADE.md. **Version check:** the api answers 503 `version_mismatch` (it refuses requests, it does not refuse to start) when the web image is a different version, and the web shows a full-page message. The e2e stack switches the check off from the start, so no test contacts GitHub. Release assets are attached as `env.example` (GitHub had uploaded `.env.example` as `default.env.example`); INSTALL step 1 says so.
