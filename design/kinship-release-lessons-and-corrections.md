# KinShip: release lessons and corrections to older docs (split out of the handoff on 2026-11-22)

Companion to `kinship-build-status-and-handoff.md`, which stays the current state. This file holds the release process lessons from 0.2.1, the list of lines in older docs and the mockup that are stale (with what has been fixed), and the release-prep reminders for 0.3.0 including the hand-written What's new sentences. Where this file and the handoff differ, the handoff wins.

## Release process lessons from 0.2.1 (the first release made with release-please)
- **Commit types on `site/` decide the version.** release-please reads every commit since the tag. `feat(site):` #114 and #115 (and `fix(site):` #116) were counted: it proposed 0.3.0 and listed them under Features. An `exclude-paths: ["site"]` entry could not help, because #114 also changed `.github/` and `.prettierignore` and #115 also changed `eslint.config.mjs`. Main is linear and protected, so the commits cannot be rewritten. **Rule (also in CLAUDE.md): a website-only change is `docs(site):` or `chore(site):`, never `feat` or `fix`.** #123 tracks a CI check for it.
- **How 0.2.1 was forced.** A `Release-As: 0.2.1` footer in the squash message of the screenshots PR (#122, a `docs:` commit), then a hand-edited release PR (#117): the CHANGELOG section and the PR body list only the two fixes.
- **What may still need a hand edit on a release PR:** (1) the `.release-please-manifest.json` formatting is fixed by #124. (2) The `[Unreleased]` ordering is fixed by #130 (the empty heading was removed); **the next release PR is the real proof, and the rollback is putting the heading back**; ADR 0017 says all this. UPGRADE.md keeps its own "Unreleased (will become x.y.z)" convention. (3) Hidden commit types can still appear in the generated changelog (the #122 Documentation line) and must be removed by hand. (4) Read the CHANGELOG section and the PR body before merging, because the GitHub Release notes and the in-app What's new popup are built from the CHANGELOG section.
- **Merge nothing else into `main` before the release PR.** release-please rewrites the PR and its changelog on every push to `main` and would undo the hand edits. Check that the release branch is 0 commits behind `main` before merging it.
- **After the release PR is merged and before the tag,** release-please's run on `main` aborts with "There are untagged, merged release PRs outstanding" while the merged release PR still carries `autorelease: pending`. `skip-github-release` means release-please never swaps it to `autorelease: tagged`, so someone must, and the repo had no `autorelease: tagged` label at all (created by hand Nov 24, grey, release-please's own name). **Learned at 0.3.0: leave the label `pending` until the GitHub Release exists, then swap it.** Swapped early (before the tag), the next release-please run finds no release to stop at, rescans all history (620 commits) and could open a bogus release PR; pending, it just aborts, which is harmless. At 0.3.0 #117 was swapped when starting the final (needed: otherwise release-please opens no release PR) and #276 was swapped before the tag with nothing merged meanwhile, which was safe but is the wrong order. CONTRIBUTING and ADR 0037 say after. The label list can lag: check each PR directly. #228 will automate this.
- CI started on its own on #117 after Claude Code pushed to it (no close and reopen was needed this time, unlike the note in "Next", item 1; ADR 0017 still lists the reopen workaround, so keep it in mind).
- **The upgrade test needs `scripts/upgrade-test/seed-<version>.sh` for every published release, even a patch with no migration.** After 0.2.1 was published, the required check "Upgrade test (previous release)" failed on every branch cut before #126 added `seed-0.2.1.sh` (#124 hit it; the fix was to merge `main` into the branch, never to rebase or force-push). Add the seed right after publishing, before the next PR (#127 put it on the release checklist in CONTRIBUTING and ADR 0016), and start new branches from current `main`.
- The line "ERROR: current user cannot be dropped" also appears in passing upgrade-test runs (once per pinned upgrade path): cleanup noise, not a failure.
- Squash and merge titles must be Conventional Commits. #128's title ("Docs/sync website and handoff") was not; release-please ignores it, but it would fail the check proposed in #123.

## Release candidate lessons from 0.3.0-rc.1 and rc.2 (Nov 22 to 23)
- **rc tags are hand-made** (ADR 0037). `.release-please-manifest.json` stays at the last stable (0.2.1) until the final. Tags are annotated, unsigned, and `v*` tags cannot be moved or deleted.
- **Exact headings.** `scripts/release-info.mjs` needs `## <version>` in UPGRADE.md and `## [<version>] - date` in CHANGELOG.md for each tag. **Each rc renames the UPGRADE block** (`## 0.3.0-rc.1`, then `## 0.3.0-rc.2`), and the block must become `## 0.3.0` before the release-please PR for the final (the preview is strict for that PR).
- **"tag it" before the version PR is merged stops at pre-flight.** Claude Code checks that the version PR is merged and last, versions match, headings exist, the tag does not exist, and release-info passes in strict mode. Fix: merge the version PR, then say "tag it" again. Nothing is tagged on a failed pre-flight.
- **Version comparison.** A pre-release compares with the highest earlier tag (rc.2 against rc.1). A stable release compares with the highest earlier **stable** tag, so the final v0.3.0 compares with v0.2.1: breaking and migration are true and people on 0.2.1 are warned.
- **The upgrade test per rc.** Add `seed-<version>.sh` (a wrapper that sources `seed-0.3.0.sh`) before tagging, and after the tag open a `ci: pin the <tag> upgrade path` PR that adds `PREVIOUS_TAG` for it and keeps the earlier pins. Pins now: v0.1.0-alpha.2, v0.2.0-rc.1, v0.2.1, v0.3.0-rc.1, v0.3.0-rc.2, v0.3.0-rc.3, v0.3.0-rc.4 (pin PR #272), v0.3.0 (pin PR #277; until the next release the unpinned first step also starts from v0.3.0, so that upgrade runs twice). The rc.3 and rc.4 wrappers leave `SEED_PARTICLES` off (their API refuses `surnameParticle`); only the rc.1 and rc.2 pins keep it and test the fold. The upgrade job takes about 10 minutes of a 30-minute limit.
- **Safety copy name.** Upgrading to 0.3.0 from 0.2.1 makes `pre-upgrade-0016-to-0024.tar.enc` (migrations 0017 to 0024, since migration 0024 in step 43; it was `0016-to-0023` before). An rc.1 or rc.2 install moving to rc.3 or the final makes `pre-upgrade-0023-to-0024.tar.enc`. The UPGRADE blocks must say so.
- **Website workflow.** After a Release run the Website workflow failed with "Found 0 artifacts" (an upstream race, actions/deploy-pages#451). #232 split it into "Build the website" and "Publish the website" jobs; the rc.2 release run was its first real proof and it passed.
- **Release job failures.** Stop and report the log excerpt; never retry or re-tag. A known flaky test failing in `checks` with nothing pushed is JC's call (re-run failed jobs), never a re-tag.
- **Merge freeze.** Nothing merges between the release PR being opened and the tag (release-please rewrites the PR on every push to `main`). For 0.3.0 the `design/` mirror PR (#275) merged BEFORE the #117 label swap, so nothing else merged once release PR #276 existed. Restore is SuperAdmin only, so What's new says "SuperAdmins can restore a backup".
- **Final 0.3.0 (step 47, done Nov 24), the order that worked:** (1) website PR #273 and UPGRADE PR #274 (the four rc blocks merged into one `## 0.3.0`); (2) the `design/` mirror PR #275; (3) swap #117's label (create `autorelease: tagged` first) and run `gh workflow run release-please.yml --ref main`, which opened #276 (0 behind main, one commit, no CI until Claude Code pushes); (4) hand-edit the CHANGELOG section (heading `## [0.3.0] - <merge date>`, a Breaking change sentence, Added, Changed, Fixed, 3,346 characters, standing alone because What's new hides rc sections once 0.3.0 exists) and the PR body, push, wait for the 7 required checks and the Release dry run (`breaking=true`, `migration=true`, `previous=v0.2.1`, `latest: true`; anything else is a stop); (5) JC squash-merges #276 (f051a43), CI on `main` green; (6) "tag it": annotated unsigned `v0.3.0` on f051a43, Release run all green (checks, prepare, both images, smoke test, GitHub Release); verify the Release is latest and not a pre-release, both images carry `0.3.0`, `0.3`, `latest`, `sha-<7>`, and the website shows 0.3.0; (7) follow-ups: pin PR #277, docs PR #278 (status lines in CLAUDE.md, README, CONTRIBUTING, ADR 0017 and 0037), and the closable-issue list (JC closes). **The final is `breaking=true` against 0.2.1 because of the `feat!` #140 (names), expected.** The rc.4 UPGRADE block was added above rc.3 (not a rename) and the final merged all four. Left for later: the demo line (`site/demo/index.html:55`) after JC upgrades the demo, and the stale mockup, requirements and tree-settings doc lines below.
