## How we work
- JC builds in VS Code with Claude Code. In chat, Claude acts as advisor and reviewer: reads Claude Code's step reports (JC attaches them as text files), confirms or changes its decisions, updates this doc after each merged step, and writes the next prompt.
- Each prompt: work on a branch, open a PR, merge once CI is green, sign off every commit with `git commit -s` (git config supplies it; never type the sign-off or an email by hand, step 10's squash message did and put JC's email in a public commit), report decisions made on JC's behalf, known gaps, and exact CI job names. Keep the Claude co-author line in squash/merge messages. Claude Code stops before irreversible steps (publishing, releases) and waits. **It creates and pushes a release tag only when JC says "tag it"** (annotated and unsigned, `git tag -a`, on the merged `main` commit), never moves or deletes a `v*` tag, never force-pushes, and reports a failed release job with the log excerpt instead of retrying or re-tagging (ADR 0017, Exceptions: only JC may delete a tag, and only when its release run failed before anything was published).
- Bigger steps run in two phases: phase 1 is read-and-report only, then JC says "go" for phase 2. **Claude Code sessions expire, so prompts must be self-contained** (carry the approved design and decisions in the text, and say which source wins where they differ).
- The design docs are maintained here, in the Project, and mirrored one way into the repo's `design/` folder. **Claude Code must never edit `design/`**: `.claude/settings.json` denies its edit and write tools there, and `CLAUDE.md` forbids shell edits too. If a doc is stale, Claude Code reports it. The rules for keeping the two in step are in the next section.
- Standing preferences: **no AI features by default, with one approved, optional exception (JC, Nov 16): automatic transcription of handwritten scans, off until an admin connects an engine and asked per upload.** Reports, summaries, duplicate detection and person matching stay fixed rules, with nothing invented. Interface wording is "Automatic transcription", not "AI". Full design in `kinship-transcription-engines-and-matching.md`. Docker Compose files are named `compose.yml`; three services (web, api, db).
- Claude can use the built-in browser for GitHub settings (GitHub may ask JC to confirm with a passkey or TOTP).
- GitHub sometimes does not start CI on a new PR until it is closed and reopened.
- **Claude Code stages explicit paths only** (never `git add -A` or `git commit -a`) and runs `git status` before each commit, because JC's own uncommitted work can sit in the same checkout: on Nov 21 a `git add -A` swept an untracked `apps/docs/` and a lockfile change into #189 (see "Open after step 35"). Every prompt carries this rule.

## How we keep docs in sync
The Project is the source of truth and `design/` is a one-way mirror. Nothing syncs automatically (neither side can see the other), so the rules are:
1. **Push at the moment of change.** When Claude edits a Project doc in chat and the desktop app is linked, it writes the same file into `design/` in the same turn and names the files. JC commits them as separate signed-off `docs:` commits and never leaves `design/` changes uncommitted while Claude Code switches branches (a stash once dropped them).
2. **Drift check before a build prompt and after each merged step.** Claude compares `design/` with the Project (first and last lines, section markers, sizes; not a byte hash) and runs `git status --short design/` through the connected folder when it can. Differences are fixed before the next prompt is written. If the folder is not linked, Claude says the check could not run.
3. **One writer per direction.** Docs are edited only in the Project. Claude Code never edits `design/` and reports a stale doc instead; if a correction is needed, it goes in the prompt text or an ADR in `docs/decisions/`. When the two disagree, the newer Project text wins, **unless it drops a decision JC accepted**: check against `CLAUDE.md` and this note before overwriting either side (on Nov 18 the Project's release plan had lost the accepted support policy and release-please lines; the repo copy kept them).
4. **The sync line above is part of every sync.** Update its date and any exceptions whenever files are pushed.
5. **The mockup is synced at milestones, not on every edit.** It is a 370 KB artifact that cannot be copied through chat reliably. JC downloads the artifact (a zip: `index.html`, `patch-tr.js` and two scans), unzips it in `/tmp`, and copies **only `index.html`** over `design/kinship-mockup.html` on its own branch, after checking the file for real names (`patch-tr.js` and the scans hold real data and must never be committed). The sync line records the artifact version it matches. When Claude changes the mockup in chat it edits the artifact (`edit_version`) as well as the repo copy, so the next export keeps the change.
6. **Optional guard, not yet set up:** a CI or `CODEOWNERS` rule that `design/` changes come only in `docs:` commits by JC. Add it only if drift keeps happening.

  - People have `secondSurname` and `marriedSurname`; a new search column replaces `people.search_name` (the old column stays until #33).

- Adoption (ADR 0007): `person_parents` primary key is `(child_id, kind)`, `kind` `birth` or `adoptive`, plus `link_date` and precision. No private flag. `users.lineage_view` (`adoptive` default) is the viewer's own setting, changed by `PATCH /api/auth/me` and now also on My settings, Family. `kinship_effective_links(view)` decides which set applies; the tree API takes the viewer's view or `?lineage=`. Helpers for later privacy work: `kinship_parent_ids_of_kind`, `kinship_birth_parent_ids`, `kinship_legal_parent_ids` (adoptive set if any, else birth); medical, DNA and identity-number logic read link kinds, never the viewer's setting. Only admins add adoptive links; a Member's added children are birth links. A person may be in both sets only as a partner in the adoptive set's union (step-parent adoption). `parent_too_young` warns for birth links only.
- Permissions: SuperAdmin and Family Admin edit everything; Member edits their own person plus people they created in their own line (both kinds; no delete), adds birth children in their own line, updates status/dates of unions that include them; User is read-only.
- **Restore from the app and maintenance mode (ADR 0031, step 36; PRs #198 to #204; no migration):** Admin -> Backups lists archives with a Restore button; the CLI shares the same check and execute code (refactored in #198). **Two steps:** the check step (SuperAdmin session, 6 a minute, no password) verifies the archive and returns a summary and warnings; the restore step needs a single-use ticket (60 seconds, in the POST body), the typed word RESTORE and the password. Only listed encrypted archives (no upload); the passphrase comes from config only. **Refused:** a backup carrying files until step 37 (issue #205), a newer schema than the app, a newer Postgres major, free space under twice the database size (CLI too). An older schema is allowed and migrated afterwards; a newer app version with a known schema is allowed with a warning. **How it runs:** in the api process behind a gate (every request but health and `GET /api/maintenance` gets 503 `maintenance`, Retry-After 5), drain (30 second cap), jobs stopped, the app pool closed, a `pre-restore-<ts>` safety dump, the schemas rebuilt (the `users` table is never edited and no trigger is disabled: the two last-SuperAdmin triggers are created after the COPY, and a backup from before 0019 gets them from the post-restore migration), result written to `state.json` (`restores` list, last 20), then the api exits (0 on success, 1 on failure) and Docker restarts it. Failures before the pool closes lift the gate with no restart. `GET /api/maintenance` touches no database; `/api/health` answers 200 `{status:'maintenance'}` meanwhile. Phases: idle, pausing, safety_copy, replacing, migrating, finishing. Accounts deleted or disabled since the backup come back active with the backup's passwords (the dialog and result page warn). New error codes: `restore_busy`, `restore_failed`, `restore_ticket_invalid`, `invalid_restore_word`, `maintenance`. Timings: Hale family 1.9 to 2.1 s, 2,011 people 1.8 to 2.0 s, CLI at 50,000 people 2.8 s, journey 15 17 s including the restart. The scheduler marks itself busy during scheduled backups too. A failed post-restore migration leaves an older-schema database and the api will not start (no automatic rollback). Two api containers fail closed but nothing tells the other to pause.
- **Dates and week start (ADR 0032, migration 0020, step 36):** a calendar picker of our own (ported from closed draft PR #92) next to the typed date field, which stays primary; it writes `YYYY`, `YYYY-MM` or `YYYY-MM-DD`. `users.week_start` (`sunday` default, `monday`, `saturday`; API `weekStart`, error `invalid_week_start`) is set in My settings, Display; it is not in the chart gear panel and not in the wizard's screens (the API accepts it at setup).
- Accounts: role change, disable, enable and delete (ADR 0029, migration 0019, step 35; build detail in `kinship-build-history.md`). `users.disabled_at` (NULL means active) is the one "disabled" flag; the login, session and reset functions refuse a disabled account, and its sign-in answers exactly like a wrong password. **Who may do what:** a SuperAdmin sets Family Admin, Member or User on any other account; a Family Admin switches Member and User accounts only; no promote action and a role change never targets a SuperAdmin in 0.3; a SuperAdmin disables, enables or deletes any other account, a Family Admin only Member and User accounts; delete needs the account disabled first and its typed email; nobody acts on their own account. Check order: self (KS045), matrix (KS020), last SuperAdmin (KS044). **The last active SuperAdmin cannot be demoted, disabled or deleted** (a count under an advisory lock in the functions, plus two row triggers on `users` as a backstop for any route; the escape is `ALTER TABLE users DISABLE TRIGGER`, named in the ADR). Routes: `PATCH /api/admin/accounts/:id/role`, `POST .../disable`, `.../enable`, `GET .../delete-preview`, `POST .../delete` (the email goes in the body). Delete removes the account and its accepted-invitation rows, never the person or the record; `created_by` columns are SET NULL. A role change needs no sign-out; disable deletes the account's sessions and revokes its set-password link; enable leaves old sessions dead and the old password works again. Invitations made by a later-disabled or deleted admin stay valid (known limit). **Rules for later releases:** 0.4's group-driven role changes must check for the last SuperAdmin before updating and must read `users.disabled_at`; shares and access for health records and identity numbers are keyed by person and resolved through `users.person_id` at read time (0.5 and 0.6). **#183, a 0.6 blocker: an admin can link a new account to a living person who has no account, which from 0.6 would expose that person's private record.**
- API contract in `packages/shared/src/people.ts`. `GET /api/people/:id` returns `permissions`, `hasAccount`, `parents: {birth, adoptive}`, unions with `children: [{id, kind, link}]`, `labels`, and `partnerChildren` (children of the person's partners who don't hang from the person: child, other parent as a person or null, link kind, `adopted` flag; follows the viewer's lineage view; one batched query). The tree response collapses a relationship with someone not drawn into "the partner alone", which is why `partnerChildren` exists.

## Decision on single sign-on (JC, Nov 18)
- **SSO is provider-agnostic OpenID Connect.** Authentik is the provider JC deploys and tests with, so it is the reference setup in the docs, not the only supported provider. Public wording: "OpenID Connect, tested with Authentik".
- **Group membership claims set the role** (the highest mapped role wins; an unmapped person gets User; accounts are created on a first SSO sign-in; SSO sessions last at most 24 hours). **Decided (JC, Nov 18):** SuperAdmin by group is allowed only with a local break-glass password (`OIDC_ENABLED=false`, restart, sign in locally) and TOTP for every SuperAdmin (ships in 0.4, with recovery codes and a CLI reset; an SSO sign-in is never asked for a code); more than one SuperAdmin is allowed, only the OIDC group can make one, and the last SuperAdmin can never be demoted, disabled or deleted; an SSO sign-in links automatically to an existing local account with the same email (verified email, case-insensitive, no existing SSO identity, never a disabled account, a change-history entry, a warning before a link lowers a role); **SSO is enforced** while `OIDC_ENABLED=true` (every local password sign-in is refused; the only way back is `OIDC_ENABLED=false` and a restart); TOTP for other roles is open (proposed 1.4). The full mechanics are in `kinship-sso-oidc.md`.
- Settings are environment variables (proposed names: `OIDC_ENABLED`, `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_PROVIDER_NAME`, `OIDC_SCOPES`, `OIDC_GROUPS_CLAIM`, `OIDC_GROUP_SUPERADMIN`, `OIDC_GROUP_FAMILY_ADMIN`, `OIDC_GROUP_MEMBER`, `OIDC_GROUP_USER`). ## Release process lessons from 0.2.1 (the first release made with release-please)
- **Commit types on `site/` decide the version.** release-please reads every commit since the tag. `feat(site):` #114 and #115 (and `fix(site):` #116) were counted: it proposed 0.3.0 and listed them under Features. An `exclude-paths: ["site"]` entry could not help, because #114 also changed `.github/` and `.prettierignore` and #115 also changed `eslint.config.mjs`. Main is linear and protected, so the commits cannot be rewritten. **Rule (also in CLAUDE.md): a website-only change is `docs(site):` or `chore(site):`, never `feat` or `fix`.** #123 tracks a CI check for it.
- **How 0.2.1 was forced.** A `Release-As: 0.2.1` footer in the squash message of the screenshots PR (#122, a `docs:` commit), then a hand-edited release PR (#117): the CHANGELOG section and the PR body list only the two fixes.
- **What may still need a hand edit on a release PR:** (1) the `.release-please-manifest.json` formatting is fixed by #124. (2) The `[Unreleased]` ordering is fixed by #130 (the empty heading was removed); **the next release PR is the real proof, and the rollback is putting the heading back**; ADR 0017 says all this. UPGRADE.md keeps its own "Unreleased (will become x.y.z)" convention. (3) Hidden commit types can still appear in the generated changelog (the #122 Documentation line) and must be removed by hand. (4) Read the CHANGELOG section and the PR body before merging, because the GitHub Release notes and the in-app What's new popup are built from the CHANGELOG section.
- **Merge nothing else into `main` before the release PR.** release-please rewrites the PR and its changelog on every push to `main` and would undo the hand edits. Check that the release branch is 0 commits behind `main` before merging it.
- **After the release PR is merged and before the tag,** release-please's run on `main` aborts with "There are untagged, merged release PRs outstanding". That is expected; it clears once `release.yml` runs on the tag, and it opens no new release PR.
- CI started on its own on #117 after Claude Code pushed to it (no close and reopen was needed this time, unlike the note in "Next", item 1; ADR 0017 still lists the reopen workaround, so keep it in mind).
- **The upgrade test needs `scripts/upgrade-test/seed-<version>.sh` for every published release, even a patch with no migration.** After 0.2.1 was published, the required check "Upgrade test (previous release)" failed on every branch cut before #126 added `seed-0.2.1.sh` (#124 hit it; the fix was to merge `main` into the branch, never to rebase or force-push). Add the seed right after publishing, before the next PR (#127 put it on the release checklist in CONTRIBUTING and ADR 0016), and start new branches from current `main`.
- The line "ERROR: current user cannot be dropped" also appears in passing upgrade-test runs (once per pinned upgrade path): cleanup noise, not a failure.
- Squash and merge titles must be Conventional Commits. #128's title ("Docs/sync website and handoff") was not; release-please ignores it, but it would fail the check proposed in #123.
