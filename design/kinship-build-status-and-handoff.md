# KinShip: build status and handoff (as of 2026-11-17, after v0.1.0-alpha.2 and 0.2 steps 12 to 17)

Read this first in a new chat. The design docs in this Project remain the source of truth for product decisions; this note records where the build stands and how we work.

## How we work
- JC builds in VS Code with Claude Code. In chat, Claude acts as advisor and reviewer: reads Claude Code's step reports (JC attaches them as text files), confirms or changes its decisions, updates this doc after each merged step, and writes the next prompt.
- Each prompt: work on a branch, open a PR, merge once CI is green, sign off every commit with `git commit -s` (git config supplies it; never type the sign-off or an email by hand, step 10's squash message did and put JC's email in a public commit), report decisions made on JC's behalf, known gaps, and exact CI job names. Keep the Claude co-author line in squash/merge messages. Claude Code stops before irreversible steps (tags, publishing) and waits; JC runs the tag commands himself.
- Bigger steps run in two phases: phase 1 is read-and-report only, then JC says "go" for phase 2. **Claude Code sessions expire, so prompts must be self-contained** (carry the approved design and decisions in the text, and say which source wins where they differ).
- The design docs are maintained here, in the Project, and mirrored one way into the repo's `design/` folder. When the desktop app is linked, Claude pushes each changed doc into `design/` after updating the Project and says which files; JC commits them. **Claude Code must never edit `design/`**: `.claude/settings.json` denies its edit and write tools there, and `CLAUDE.md` forbids shell edits too. If a doc is stale, Claude Code reports it. A copy in `design/` can still lag if Claude was not linked; check file dates when in doubt.
- Standing preferences: **no AI features by default, with one approved, optional exception (JC, Nov 16): automatic transcription of handwritten scans, off until an admin connects an engine and asked per upload.** Reports, summaries, duplicate detection and person matching stay fixed rules, with nothing invented. Interface wording is "Automatic transcription", not "AI". Full design in `kinship-transcription-engines-and-matching.md`. Docker Compose files are named `compose.yml`; three services (web, api, db).
- Claude can use the built-in browser for GitHub settings (GitHub may ask JC to confirm with a passkey or TOTP).
- GitHub sometimes does not start CI on a new PR until it is closed and reopened.

## Repo
- `officialJCReyes/kinship`, public, AGPL-3.0. `CLAUDE.md` at the repo root holds the rules for Claude Code. Install guide is `INSTALL.md` at the repo root; `UPGRADE.md` and `CHANGELOG.md` exist; README has screenshots from `docs/assets/screenshots/` (made on demand with `pnpm --filter @kinship/e2e screenshots`, not in CI). The logo kit is in `design/brand/`, `docs/assets/` and `apps/web/public/`; the logo and name are not AGPL-licensed (TRADEMARK.md).
- Stack (ADR 0001/0002): PostgreSQL 18, TypeScript API on Node 26 (Fastify, Kysely, plain numbered .sql migrations), React 19 + Vite web served by unprivileged nginx 1.30, pnpm 12 via corepack, Vitest, Playwright.
- Auth (ADR 0003): setup token printed in the api log, argon2id, server-side sessions, CSRF header + Origin check, sign-in rate limits (30 requests a minute on the sign-in route for the whole e2e run), email is the sign-in name, the `kinship` CLI (a command table: `set-password <email>`, `backup`, `backup-list`, `backup-verify`, `backup-decrypt`, `restore`). Row-level security: app role is non-owner with no BYPASSRLS; secrets reachable only via SECURITY DEFINER functions.
- Invitations and passwords (ADR 0012, migration 0011): `account_links` (kind `invite` or `reset`; only the SHA-256 of the token is stored; single use; revoke; regenerate replaces the token in the same row; RLS enabled but not forced, no policies and no grants for the app role, so all access is through SECURITY DEFINER functions that check the caller's role). Invitations last 7 days; admin set-password links last 24 hours. One open invitation per lowercased email and per person; one open set-password link per account. **Who may do what:** SuperAdmin invites Family Admin, Member and User; Family Admin invites Member and User; nobody invites a second SuperAdmin; set-password links: a Family Admin for Members and Users only, the SuperAdmin for anyone except themselves (a locked-out SuperAdmin uses the CLI). An invitation may name an existing person with no account (a Member with no person is read-only; the dialog warns). Links are `/invite#<token>` and `/reset#<token>`: the fragment never reaches nginx or a Referer, the page strips it with `history.replaceState`, and the token travels only in POST bodies (checked in a real web image: nginx log token count 0). Links are shown once (closing the dialog loses it; "make a new link" regenerates). Every bad link (unknown, expired, used, revoked) gives the identical 404 `invalid_link`. Limits: link routes 20 failures per IP and 200 global per 15 minutes; password change 10 per account and 20 per IP. `POST /api/auth/password` deletes the account's other sessions and rotates the current token; a self change or the CLI retires any open set-password link for that account. `users` also has `last_sign_in_at`, `password_changed_at` and `password_changed_via` (`setup`, `self`, `admin_link`, `cli`, `invitation`; null means not recorded, for old accounts); the Account card shows "Password last changed ... using ..." so an owner can see an admin link did it (from 0.6 an account's private medical record is readable by whoever controls the account). Admins read all `users` rows through `users_select_admin` (the hash has no column grant). Email is unique ignoring case (`lower(email)` index).
- First-run wizard (ADR 0013, migration 0012): seven steps (Account, Tree, You, Partner, Parents, Children, Review). **Nothing is written until Review**: the wizard keeps everything in memory (no localStorage or sessionStorage except the color-scheme mirror), a refresh restarts it, and `POST /api/setup` creates the account, tree, people and relationships in one transaction through `kinship_auth.complete_setup_family` (advisory lock plus a "no users" re-check, so exactly one concurrent finish wins; any failure rolls back everything). The token is typed in step 1 and checked early by `POST /api/setup/check` (204 or 403 `invalid_setup_token`, sharing the setup failure limiters), then sent again with the final post. Every setup error carries a `field` path (`family.children.1.birth`) that the web maps back to a step and field. Skip is allowed on Partner, Parents and Children, not on You; gender is optional everywhere ("Not specified" is null); the partner has Living or Deceased (Widowed requires Deceased; Married plus Deceased becomes Widowed automatically); when both parents are entered a "their relationship" select (default Married) sets their union; children choose the partner or "Not on the tree" (hidden with no partner; cap 30); all links are birth links. Warnings (`parent_too_young`, same name and birth date) are soft and not stored. Setup lands on `/tree/{you}`. The legacy `person` field still works for scripted installs but cannot be combined with `family`. Migration 0012 dropped the 5-argument `complete_setup` (#9); the 7-argument one stays until a later contract step.
- Backups and the safety copy (ADR 0014, migration 0013; PRs #66 to #72): **the api keeps the owner credentials for maintenance jobs** (amends ADR 0001; they are removed from `process.env` after config load, passed only in a child process's explicit environment, never in argv or logs; `/proc/<pid>/environ` still holds them, as the ADR says). A dump runs `pg_dump -Fc --no-owner` as the OWNER role in a short-lived child (the image has `postgresql18-client`, +9 MB, PostgreSQL License), only if the owner has `rolsuper` or `rolbypassrls`; otherwise a backup refuses with the exact `ALTER ROLE ... BYPASSRLS` fix (in INSTALL.md) and the pre-migration safety copy is SKIPPED with a recorded reason (so those installs can still upgrade); a real dump failure on a capable owner blocks the migration. Archive `kinship-YYYY-MM-DD-HHMM.tar.enc` (UTC; `-2` suffix inside one minute): tar of `manifest.json`, `database.dump`, `files/` (slot only; no media exists yet); authenticated cleartext header (format, app version, schema number, KDF parameters); scrypt (N=2^17, r=8, p=1) plus HKDF, AES-256-GCM in 64 KiB chunks with a final-chunk flag in the AAD; a wrong passphrase is told apart from corruption or truncation before any restore step. Manifest has per-table counts and digests under one snapshot and an RLS and grants fingerprint (one SQL query, also run inside the restore transaction). `BACKUP_PASSPHRASE` (or `_FILE`), 16 characters minimum, `change-me-backup` refused; `BACKUP_ENABLED=on` is the master switch for the schedule only; `BACKUP_DEST` accepts only `local` (s3 is 1.1). Recovery without KinShip: standalone `kinship-decrypt.mjs`, the format spec in `docs/`, `kinship backup-decrypt` (plain openssl cannot decrypt chunked GCM). **Restore is CLI only** (`docker compose stop web api`, then `docker compose run --rm api kinship restore <file>`): preflight (full verify in a work folder on the backups volume, refuse newer schema, newer Postgres major, role-name mismatch, open app-role connections, low disk), typed `RESTORE`, a `pre-restore-<ts>` safety dump, `ensureAppRole` first (so it works on a brand-new empty Postgres), then one explicit `BEGIN ... COMMIT` script (drop and recreate schemas, restore, verify counts against the manifest, delete all sessions, revoke open `account_links`), then migrations if the backup is older, then an `upgrade_log` row. The CLI executes only authenticated archives, never plain `.sql.gz` copies (manual psql steps are documented). "Test the latest backup" restores into `kinship_verify_<hash of db name>_<random>` as the owner (degrades to decrypt, tag and manifest checks without CREATEDB), compares counts, digests, fingerprint and migration checksums, runs a functional check as the app role, and always drops the database (plus a startup sweep). Scheduler: a 60-second tick in the api, catch-up two minutes after start, Postgres advisory lock plus a lock file, temp file then rename, mode 0600 (folder 0700), free-space check, retention daily/weekly/monthly 7/4/6 by default (only our file names; the newest good archive is never deleted; `pre-upgrade-*` and `pre-restore-*` keep 3 each), history in `state.json` on the volume (written atomically; a restore cannot rewind it). **Safety copy before migrations (on by default; `app_settings` key `safety_copy`, read safely when the table does not exist yet):** dumps before any pending migration on a database that already has applied ones, verified by reopening, named by schema numbers (`pre-upgrade-0012-to-0013`), `.tar.enc` in the same archive format when a passphrase is set, otherwise plain `.sql.gz` mode 0600 with a warning. Break-glass: one-shot `KINSHIP_SAFETY_COPY=skip` (only that value; documented in INSTALL and UPGRADE troubleshooting, logged and recorded). Tables: `app_settings` (SuperAdmin-only RLS, allow-listed keys with shared parsers; step 17 adds the update-check toggle) and `upgrade_log` (event migrate or restore, from and to schema number and version, the safety-copy file name or `safety_note`). Migration 0013 also fixed #35 (the three owner-only widow policies now test membership of the table owner, not a hardcoded role name). Backups folder: bind mount `./data/backups:/var/lib/kinship/backups`; Linux needs `mkdir -p data/backups && sudo chown 1000:1000 data/backups` (the api checks and prints the command, and for an unmounted folder prints the exact compose lines); compose healthcheck `start_period` is 600s so a long safety copy is not reported unhealthy; `scripts/smoke-test.sh` creates `data/backups` first. Routes (SuperAdmin only, `requireSuperAdmin`, `BACKUP_ROUTES` in `packages/shared`): list and status, run now (202, poll), test, settings get and patch, download ticket, download. Download re-asks the password and returns a single-use 30-second ticket bound to session and file; plain safety copies are listed but never offered for download. `ensureAppRole` now runs under the migration lock and changes only the password unless role attributes are unsafe.
- Updates (ADR 0015, migration 0014; PRs #75 to #83): Admin -> Updates (SuperAdmin; a Family Admin sees the tab with a note only). The daily check runs in a small shared job runner (built in step 17; the backup scheduler and the 0.4 birthdays job can use it): conditional requests (ETag), allow-listed redirects, size and time limits, back-off, rate-limited Check now, `HTTPS_PROXY` honored (tested against a local proxy), nothing sent when the switch is off, no data about the install sent. The toggle is `app_settings` key `updates.check` (in-app, default on; there is no environment variable); Include pre-releases (off) and the safety-copy switch (`safety_copy`) sit next to it. The scheduled check rereads the next-check time from the database when due; turning the switch on makes the next tick check at once. Each GitHub release carries a `release-manifest.json` made by the pipeline (generator, validator and dry-run artifact built in step 17; a stable release is compared with the latest earlier tag of any kind; the CHANGELOG heading reader accepts the Keep a Changelog and release-please forms; `upgradeFrom` is always null). The app offers every stable release newer than the running version and combines the flags. Migration 0014 adds `update_check`, four per-account columns (last seen version, banner and backup-gate memory) with a trigger so new accounts start current, and `upgrade_log.backup_version`; a restore logs the version that was running before. Seven SuperAdmin routes plus `GET /api/updates/whats-new?latest=1` for the About button. Web: Updates tab, banner on Admin pages, "What's changing" popup (each release's own Markdown, not regrouped; backup warning and the soft gate with the "I have a backup I can restore" tick), "What's new" popup for every admin after an update (regrouped from the bundled CHANGELOG; migration note and safety copy name from `upgrade_log`; downgrade notice), About page with a What's new button. Markdown from the internet is rendered by an own inert renderer (no raw HTML, no new dependency; scans capped at 2,000 characters after CI caught a quadratic case). The api image now carries CHANGELOG.md and UPGRADE.md. **Version check:** the api answers 503 `version_mismatch` (it refuses requests, it does not refuse to start) when the web image is a different version, and the web shows a full-page message. The e2e stack switches the check off from the start, so no test contacts GitHub. Release assets are attached as `env.example` (GitHub had uploaded `.env.example` as `default.env.example`); INSTALL step 1 says so.
- Release (ADR 0004): `release.yml` on `v*` tags; multi-arch images to `ghcr.io/officialjcreyes/kinship-web` and `kinship-api`; SBOM and provenance attestation; GitHub Release from CHANGELOG (a breaking-change commit requires `UPGRADE.md`); pre-releases never move `latest`. Manual releases for 0.1; release-please planned from 0.2 (step 18). A "Release dry run" workflow runs on PRs that touch the web nginx config; it pushes nothing.
- People and relationships (ADR 0005): tables `people` (`surname` is the birth surname; dates as text + precision + generated from/to), `unions` (partner relationships; remarriage allowed), `person_parents`, `users.person_id`. Max two parents per set, no cycles, a child with two unlinked parents gets an Unknown union (also for adoptive couples); deleting a union with children is refused; deleting a person needs `confirm=true` and reparents children. ADR 0005's note "automatic Widowed and step naming are not built" is superseded by ADRs 0008 and 0010.
- Names, Widowed, labels, step relatives (ADRs 0008, 0009, 0010; migrations 0007 names and Widowed, 0008 status by hand, 0009 relationship labels):
  - People have `secondSurname` and `marriedSurname`; a new search column replaces `people.search_name` (the old column stays until #33).
  - Marking a person deceased turns their Married relationships into Widowed (`statusAuto` marks automatic ones); marking them living again reverts only automatic ones, and only if the other partner is not deceased. Saving a status by hand, even the same one, makes it permanent.
  - Custom relationship labels are added by admins only. A label never changes the tree or who is next of kin. A label replaces only the derived step title for that pair, on both profiles; the family sections are never hidden.
  - Step relatives: only Married and Widowed relationships give step titles. A parent through the same relationship is never a step-parent. Divorced then remarried gives only the current marriage. Step-parents come from the tree response; stepchildren from `partnerChildren`. Titles show on the profile only (not the tree panel or the finder, which is 0.3).
- My settings (ADR 0011, migration 0010): `users` has `color_scheme` (forest default, sand, slate, graphite), `theme` (device default, light, dark), `date_format` (mdy default, dmy, dmy2, long, iso, us, eu) and `surname_choice` (married default, birth), next to `lineage_view`. The app role may read and update only these columns on its own row (column grants plus `users_update_own`); role, email, name, password and person link stay untouchable. `PATCH /api/auth/me` takes any non-empty subset of the five settings; login, `GET /api/auth/me` and setup return them as flat `AuthUser` fields. `POST /api/setup` accepts an optional `settings` object checked by the same parser (`parseUserSettings` in `packages/shared`), ready for the wizard. One shared `formatPartialDate` (no `Intl`, month names from translation keys) and a display store feed `formatDate`, `displayName` and `displaySurname`; the routed page is keyed by date format and surname choice so a change remounts it once (the settings page itself is not remounted). Themes: four schemes x light and dark as `:root[data-scheme][data-theme]` blocks; status colors, gender colors and tints are the same in every scheme; the logo-green leaf depends only on light or dark. `public/theme-init.js` (external, because the CSP forbids inline scripts) applies a `{colorScheme, theme}` localStorage mirror before first paint and resolves Device with `matchMedia`; the account is the source of truth and the mirror survives sign-out so `/login` and `/setup` keep the look. nginx serves `/theme-init.js` with `Cache-Control: no-cache` plus an ETag (and 404 if missing, never the app shell). `/api/auth/me` is refetched on every window focus. A Vitest contrast test covers all 8 combinations; one known failing pair is in its `KNOWN_BELOW_AA` list (#44).
- Adoption (ADR 0007): `person_parents` primary key is `(child_id, kind)`, `kind` `birth` or `adoptive`, plus `link_date` and precision. No private flag. `users.lineage_view` (`adoptive` default) is the viewer's own setting, changed by `PATCH /api/auth/me` and now also on My settings, Family. `kinship_effective_links(view)` decides which set applies; the tree API takes the viewer's view or `?lineage=`. Helpers for later privacy work: `kinship_parent_ids_of_kind`, `kinship_birth_parent_ids`, `kinship_legal_parent_ids` (adoptive set if any, else birth); medical, DNA and identity-number logic read link kinds, never the viewer's setting. Only admins add adoptive links; a Member's added children are birth links. A person may be in both sets only as a partner in the adoptive set's union (step-parent adoption). `parent_too_young` warns for birth links only.
- Permissions: SuperAdmin and Family Admin edit everything; Member edits their own person plus people they created in their own line (both kinds; no delete), adds birth children in their own line, updates status/dates of unions that include them; User is read-only.
- API contract in `packages/shared/src/people.ts`. `GET /api/people/:id` returns `permissions`, `hasAccount`, `parents: {birth, adoptive}`, unions with `children: [{id, kind, link}]`, `labels`, and `partnerChildren` (children of the person's partners who don't hang from the person: child, other parent as a person or null, link kind, `adopted` flag; follows the viewer's lineage view; one batched query). Tree API `GET /api/tree/:personId?up&down&collateral&lineage`: only unions with both partners drawn (invariant tested); `ancestorCount` and `otherFamily {count}` for leaves; each drawn in-law (a partner drawn only as a partner) also brings their own children that hang from them alone or from a union with someone outside the walk (one hop; the other parent and the children's descendants are not pulled in). The tree response collapses a relationship with someone not drawn into "the partner alone", which is why `partnerChildren` exists.
- Web: routes `/`, `/people`, `/people/:id`, `/tree`, `/tree/:id`, `/tree/:id?of=&lineage=` (flip), `?sel=`, `/settings`, `/admin/users` (admins only; others get not-found), Admin -> Backups (SuperAdmin only), `/invite`, `/reset`, `/about`, `/login`, `/setup`. Account menu (name and initials; My profile when linked, My settings, Admin for admins, About KinShip, Sign out; no role label or bell yet) replaces the "signed in as" bar. Profile with gendered relationship labels, both parent families, adoption banner and switch, "Step relatives" list (de-duplicated). Family tree chart (ADR 0006): own layout and SVG, pan/zoom/fit, keyboard navigation, panel, collapsible legend, couple lines that open the relationship editor, logo-green leaves (spouse's family on top; other family on the left), Center on me, picker for unlinked accounts. No crossing-reduction sweeps (#21). My settings page: Display (four swatches, theme, date format with a live example), Names, Family, and an Account card with the password trace and a Change password form. No Notifications or Coming up cards yet. Admin has the Users tab and, for the SuperAdmin, Backups and Updates tabs (Updates: version card, three switches, Check now, banner and popups, see the Updates bullet; Backups: status card, Back up now, Test the latest backup, list with Download, settings form, the command-line restore steps; no Restore button). The Users tab: list (name, email, linked person, role, status, last sign-in, password trace), Invite user dialog, show-once link dialog, make a new link, revoke, set-password link.
- Tests: Vitest; API tests against Postgres 18 (role matrix, RLS as raw SQL, API invariant property tests, seeded `partnerChildren` property test, scale and detail-size guards, migration 0010 test on populated data; 1,074 API tests, with migrations 0011 to 0014 tested on populated data; the Postgres 18 client is installed in the "Tests (Postgres 18)" job); web suite 486; script tests 34; Playwright package `e2e/` with journeys 01 to 10 plus the tree and in-law-children cases (63 tests; journey 01 is the full Hale-family wizard run, journey 11 the Backups journey, journey 12 the Updates journey with no new sign-ins; job "End-to-end (Playwright)", passed on every PR so far, not required yet).
