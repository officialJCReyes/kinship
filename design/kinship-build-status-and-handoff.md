## How we work
- JC builds in VS Code with Claude Code. In chat, Claude acts as advisor and reviewer: reads Claude Code's step reports (JC attaches them as text files), confirms or changes its decisions, updates this doc after each merged step, and writes the next prompt.
- Each prompt: work on a branch, open a PR, merge once CI is green, sign off every commit with `git commit -s` (git config supplies it; never type the sign-off or an email by hand, step 10's squash message did and put JC's email in a public commit), report decisions made on JC's behalf, known gaps, and exact CI job names. Keep the Claude co-author line in squash/merge messages. Claude Code stops before irreversible steps (publishing, releases) and waits. **It creates and pushes a release tag only when JC says "tag it"** (annotated and unsigned, `git tag -a`, on the merged `main` commit), never moves or deletes a `v*` tag, never force-pushes, and reports a failed release job with the log excerpt instead of retrying or re-tagging (ADR 0017, Exceptions: only JC may delete a tag, and only when its release run failed before anything was published).
- Bigger steps run in two phases: phase 1 is read-and-report only, then JC says "go" for phase 2. **Claude Code sessions expire, so prompts must be self-contained** (carry the approved design and decisions in the text, and say which source wins where they differ).
- The design docs are maintained here, in the Project, and mirrored one way into the repo's `design/` folder. **Claude Code must never edit `design/`**: `.claude/settings.json` denies its edit and write tools there, and `CLAUDE.md` forbids shell edits too. If a doc is stale, Claude Code reports it. The rules for keeping the two in step are in the next section.
- Standing preferences: **no AI features by default, with one approved, optional exception (JC, Nov 16): automatic transcription of handwritten scans, off until an admin connects an engine and asked per upload.** Reports, summaries, duplicate detection and person matching stay fixed rules, with nothing invented. Interface wording is "Automatic transcription", not "AI". Full design in `kinship-transcription-engines-and-matching.md`. Docker Compose files are named `compose.yml`; three services (web, api, db).
- Claude can use the built-in browser for GitHub settings (GitHub may ask JC to confirm with a passkey or TOTP).
- GitHub sometimes does not start CI on a new PR until it is closed and reopened.
- **Claude Code stages explicit paths only** (never `git add -A` or `git commit -a`) and runs `git status` before each commit, because JC's own uncommitted work can sit in the same checkout: on Nov 21 a `git add -A` swept an untracked `apps/docs/` and a lockfile change into #189 (see "Open after step 35"). Every prompt carries this rule.

## How we keep docs in sync
The Project is the source of truth and `design/` is a one-way mirror. Nothing syncs automatically (neither side can see the other), so the rules are:
1. **Push at the moment of change.** When Claude edits a Project doc in chat and the desktop app is linked, it writes the same file into `design/` in the same turn and names the files. JC commits them as separate signed-off `docs:` commits and never leaves `design/` changes uncommitted while Claude Code switches branches (a stash once dropped them).
2. **Drift check before a build prompt and after each merged step.** Claude compares `design/` with the Project (first and last lines, section markers, sizes; not a byte hash) and runs `git status --short design/` through the connected folder when it can. Differences are fixed before the next prompt is written. If the folder is not linked, Claude says the check could not run.
3. **One writer per direction.** Docs are edited only in the Project. Claude Code never edits `design/` and reports a stale doc instead; if a correction is needed, it goes in the prompt text or an ADR in `docs/decisions/`. When the two disagree, the newer Project text wins, **unless it drops a decision JC accepted**: check against `CLAUDE.md` and this note before overwriting either side (on Nov 18 the Project's release plan had lost the accepted support policy and release-please lines; the repo copy kept them).
4. **The sync line above is part of every sync.** Update its date and any exceptions whenever files are pushed.
5. **The mockup is synced at milestones, not on every edit.** It is a 370 KB artifact that cannot be copied through chat reliably. JC downloads the artifact (a zip: `index.html`, `patch-tr.js` and two scans), unzips it in `/tmp`, and copies **only `index.html`** over `design/kinship-mockup.html` on its own branch, after checking the file for real names (`patch-tr.js` and the scans hold real data and must never be committed). The sync line records the artifact version it matches. When Claude changes the mockup in chat it edits the artifact (`edit_version`) as well as the repo copy, so the next export keeps the change.
6. **Optional guard, not yet set up:** a CI or `CODEOWNERS` rule that `design/` changes come only in `docs:` commits by JC. Add it only if drift keeps happening.

- **Restore from the app and maintenance mode (ADR 0031, step 36; PRs #198 to #204; no migration):** Admin -> Backups lists archives with a Restore button; the CLI shares the check and execute code. Two steps: a check (SuperAdmin, 6 a minute) and a restore that needs a single-use 60-second ticket, the typed word RESTORE and the password; only listed encrypted archives, passphrase from config. Refused: a newer schema or Postgres major than the app, free space under about twice the database plus both photo sets; an older schema is migrated afterwards. It runs in the api process behind a maintenance gate (503 `maintenance` except health and `GET /api/maintenance`), drains, makes a `pre-restore-<ts>` safety dump, rebuilds the schemas (the `users` table is never edited; the two last-SuperAdmin triggers are created after the COPY), writes `state.json`, then the api exits and Docker restarts it. Accounts deleted or disabled since the backup come back active with the backup's passwords. A failed post-restore migration leaves an older-schema database and the api will not start (no automatic rollback); two api containers fail closed but nothing tells the other to pause. Error codes: `restore_busy`, `restore_failed`, `restore_ticket_invalid`, `invalid_restore_word`, `maintenance`. Timings in `kinship-build-history.md`.

- **Photos, media and the file key (ADRs 0033, 0034 and 0035; migrations 0021 and 0022; step 37, PRs #209 to #218):**
  - **Key.** `FILE_ENCRYPTION_KEY` or `FILE_ENCRYPTION_KEY_FILE` (base64 of 32 bytes, or 64 hex characters). The key is **optional at startup**; there is no `FILE_ENCRYPTION=off`. Four states are shown on the Admin "Photos and files" card (`key_missing`, `files_unavailable`, `key_mismatch`, `ready`); an upload when files are unavailable answers 503 `files_unavailable` with a `reason`. **A lost key means lost photos.** Full explanation in `kinship-storage-encryption.md`.
  - **Store.** `./data/files:/var/lib/kinship/files` (`FILES_DIR`): `objects/<2 hex>/<32 hex>`, `tmp/`, `staging/`. Format KSFL v1 (64 KiB chunks, a per-file HKDF salt, an 8-byte key id); the chunk code is shared with backups (`crypto/chunks.ts`). Migration 0021 adds `media_files` (with `avatar_storage_id`, `avatar_size` and `taken_on` as `public.partial_date`), `media_people` and `people.photo_media_id`, with forced row-level security, a composite foreign key for the profile photo and three STABLE SECURITY DEFINER functions. **Migration 0022 stops forcing RLS on the owner role**: a non-superuser owner would otherwise have made the sweeper see no photos and delete every file.
  - **Sweeper.** Removes orphan files older than an hour; honours `.sweep-hold` and the backup lock; refuses to delete when no row uses any file but `objects/` holds files.
  - **Pictures.** sharp 0.35.5 (a named LGPL-3.0 exception for libvips in `scripts/check-licenses.mjs`; Alpine/musl on amd64 and arm64; the api image is about 19 MB bigger; peak memory about 150 to 210 MB at 50 megapixels). JPEG, PNG and WebP only, decided by the first bytes. Output: a 2400 px full variant and a 192 px avatar (crop `attention`), upright, no EXIF, same mime as the input. Limits: 12 MB on the wire, 10 MB as a picture, 50 megapixels, 20 uploads per 10 minutes.
  - **Routes.** `POST /api/people/:id/photos` (raw body); `GET /api/media/:id/:variant` (decrypts fully, then sends; `nosniff`, `default-src 'none'; sandbox`, immutable cache); `PATCH /api/people/:id {photoMediaId}`; `PATCH /api/media/:id {takenOn}`; list, unlink and delete routes; **`GET /api/media`** (any signed-in role, 60 a page, `?person=` and `?cursor=`, each item with `permissions`, `takenOn` and `shows`). Each photo carries `permissions: {edit, delete}` for the asking account. nginx has an upload location (`client_max_body_size 12m`, `proxy_request_buffering off`); the web image build runs `nginx -t` on every PR.
  - **Permissions.** `canEditPerson`: admins; a Member on their own person and people in their line; a User never. A Member deletes only their own uploads. Photos of living people are visible to every signed-in account. Documents and PDFs are not in 0.3.0.
  - **Date taken.** Read from EXIF (DateTimeOriginal, else CreateDate) before the strip and returned as `suggestedTakenOn`; saved only by `PATCH` as a year, a month or a day (or null); a plain typed date. Nothing else from EXIF, GPS included, is kept.
  - **Web.** `Avatar` everywhere a person is shown; the profile Photos card (upload, date taken, Set as profile photo, Remove from this person, Delete, a viewer); the delete preview names the photo count; the Media tab and `/media` page (a grid of avatar variants, person filter, "Load more", the same viewer; the viewer's person actions are offered only if the account may change that person; no lightbox arrows, upload, titles or captions). The setup Review step has a "Check for new versions" switch instead of the old update-notice paragraph (#213).
  - **Backups with photos (ADR 0033).** The archive carries `files/<storage_id>`, a `files.json` index and a manifest `files: {included, count, bytes}`; format number stays 1; `includeFiles` defaults ON; pre-upgrade safety copies stay database-only; a zero-photo backup is identical to a database-only one. A photo is staged when it is read, so one deleted during a backup is listed as missing (#217). Free space to back up: the database plus 2x the photos plus a tenth. Test the latest backup opens a random sample of up to 20 photos.
  - **Restore with photos (ADR 0035; ADR 0031 is superseded in part).** Order: key check, staging, verify, a restore-intent file, a `COMMENT ON SCHEMA public` marker written inside the database transaction, a cross-check of database against files before the commit, then the `objects` swap after the commit; crash recovery runs at the next start. A database-only restore writes a `.sweep-hold` 7 days ahead. Needs about twice the database plus both photo sets free in the backups folder. Playwright has a separate `restore` project (`retries: 0`, depends on `journeys`); journey 15 is the Restore, journey 16 is photos and the Media tab.

## Decision on single sign-on (JC, Nov 18)
- **SSO is provider-agnostic OpenID Connect.** Authentik is the provider JC deploys and tests with, so it is the reference setup in the docs, not the only supported provider. Public wording: "OpenID Connect, tested with Authentik".
- **Group membership claims set the role** (the highest mapped role wins; an unmapped person gets User; accounts are created on a first SSO sign-in; SSO sessions last at most 24 hours). **Decided (JC, Nov 18):** SuperAdmin by group is allowed only with a local break-glass password (`OIDC_ENABLED=false`, restart, sign in locally) and TOTP for every SuperAdmin (ships in 0.4); more than one SuperAdmin is allowed, only the OIDC group can make one, and the last SuperAdmin can never be demoted, disabled or deleted; an SSO sign-in links automatically to an existing local account with the same verified email (never a disabled account; a warning before a link lowers a role); **SSO is enforced** while `OIDC_ENABLED=true`. TOTP for other roles is open (proposed 1.4). Full mechanics in `kinship-sso-oidc.md`.
- Settings are environment variables (proposed names: `OIDC_ENABLED`, `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_PROVIDER_NAME`, `OIDC_SCOPES`, `OIDC_GROUPS_CLAIM`, `OIDC_GROUP_SUPERADMIN`, `OIDC_GROUP_FAMILY_ADMIN`, `OIDC_GROUP_MEMBER`, `OIDC_GROUP_USER`). Automated tests run against a mock provider, then a manual check on Authentik. Ships in 0.4. Design in `kinship-sso-oidc.md`.
