# KinShip v2 requirements (restart, Nov 2026)

Previous build (Node/Express/Prisma/React Flow) is scrapped. Mockup comes first; the stack was chosen on Nov 15 (see Decisions). Companion docs: `kinship-navigation.md` (tabs, Home, DNA badge, Add relative), `kinship-tree-views-and-dna.md` (tree views, spouse's family leaf, DNA), `kinship-color-schemes.md` (the four color schemes), `kinship-storage-encryption.md` (file encryption), `kinship-email-templates.md` (emails), `kinship-research-records-and-backup.md` (sources, places, events, stories, duplicate merge, backups), `kinship-family-health-history-report.md` (the doctor-visit report), **`kinship-surgeries-and-procedures.md` (surgeries in the medical record, added Nov 15)**, **`kinship-identity-numbers.md` (national IDs such as Cédula and CURP, and the Records request sheet, added Nov 16)**, **`kinship-adoption.md` (adoptive and biological parents, added Nov 16)**, **`kinship-sso-oidc.md` (OpenID Connect sign-in and group roles, added Nov 18)** and `kinship-release-and-deployment-plan.md` (versions, GitHub repo, Docker images, what ships when, update notice).

## Decisions
- **Stack (decided by JC, Nov 15):** **PostgreSQL 18** (supported to Nov 2030), a **TypeScript** API on Node, a separate **nginx** `web` container, and a **React** UI. Library picks inside that (Fastify, Kysely with plain SQL migrations, Vite, own SVG tree drawing) are proposed and listed in the release plan, section 6.
- Deploy: Docker Compose (file named `compose.yml`) + Postgres 18. Three services: `web` (nginx serving the static React UI, the only published port, :8080 plain HTTP, proxies `/api`), `api` (internal only, runs migrations at startup) and `db`. Same version tag for web and api. User's external reverse proxy handles TLS/certs and sees one upstream. Cloudflare optional in front only.
- **Distribution (decided by JC, Nov 15):** public GitHub repository **`officialJCReyes/kinship`, public from day one**, license **AGPL-3.0**. Images are built by GitHub Actions and published to GitHub Container Registry (`ghcr.io/officialjcreyes/kinship-web` and `kinship-api`, amd64 and arm64). Semantic versioning, 0.x releases up to a trimmed **v1.0** (core, through reports and GEDCOM); S3, MapTiler, Word, family book and DNA ship in 1.1 to 1.3. Full plan in `kinship-release-and-deployment-plan.md`.
- **Update notice (decided by JC, Nov 15; built in the mockup under Admin → Updates):** the SuperAdmin is notified when a newer version exists. **A toggle inside the app, not an environment variable; no email.** Clicking the notice opens a popup of the changes. After an update, a **"What's new" popup** shows the changelog **to every admin (SuperAdmin and Family Admins) at their next sign-in**. **If the release has a database migration or a breaking change, the popup warns the SuperAdmin to take a backup first** (shows the age of the last backup and a Back up now button). An **automatic safety copy of the database before each migration is on by default** (can be turned off in Admin → Updates). The check reads GitHub's public release list and sends nothing about the install. Details in the release plan, section 7. The account menu also has an **About KinShip** page (version, AGPL license, source-code link).
- Medical privacy enforced by Postgres row-level security (app connects as non-owner role; separate owner role runs migrations).
- Schema changes via versioned migrations, never `db push`.
- Audience: starts as one user, grows to roughly 10 to 50+ people. Public internet, login required.
- UI: English only at launch, all strings as translation keys so the community can add locales. Desktop-first dense layout, mobile-friendly. **Pages are centered in the window (Home, profile, reports, Admin and so on); only the tree canvas uses the full width (JC, Nov 14).** (The Records request sheet is the one exception to English only: its letter also has a Spanish version, see below.)
- AI features are optional and off by default (ADR 0021). The first is Automatic transcription (`kinship-transcription-engines-and-matching.md`), which stays off until an admin connects an engine. Reports, summaries, duplicate detection and person matching are generated from fixed templates and graph logic so output is repeatable and nothing is invented.
- Branding: logo kit delivered (sailboat with leaf sail; wordmark "KinShip"). Palette: deep teal #1E4D4A, leaf green #4F8A4B, amber #F2A541, cream #FBF6EE (dark-mode leaf #8CC488). **Four color schemes (Forest, Warm sand, Slate blue, Graphite) are offered to every end user, in My settings and in first-run setup (decided by JC, Nov 14); see `kinship-color-schemes.md`.** Kit includes SVG and PNG marks, horizontal/stacked/reversed logos, app icons, favicon.
- File storage is switchable: local volume or S3/S3-compatible (AWS S3, Backblaze B2, Cloudflare R2, MinIO). Files stay private and are **encrypted by KinShip before they are stored** (one key, `FILE_ENCRYPTION_KEY` or `FILE_ENCRYPTION_KEY_FILE`; there is no switch to turn encryption off); the app checks permission before it serves a file. Admin page can run a migration between backends. (Release plan: local encrypted storage for profile photos from 0.3.0, built in step 37; S3 and the migration tool in 1.1. See `kinship-storage-encryption.md`.)
- Email is switchable: Resend API or any SMTP provider. Used for invites, password resets and notifications.
- **Map tiles (decided by JC, Nov 14):** **default is OpenStreetMap when nothing is configured** (`MAP_PROVIDER` empty or `osm`, no key). Support for one keyed provider is added, **MapTiler** (my recommendation, JC accepted), chosen with `MAP_PROVIDER=maptiler` and `MAPTILER_API_KEY`. The deployer picks; more providers can be added later. The OSM public tiles are for light use only, so a busy install should switch to a keyed provider. In the mockup the **Deployment page has a Map tiles card** showing both setups, Admin → System has a preview switch, and the compose example has `MAP_PROVIDER`. (MapTiler ships in 1.1.)
- **Secrets (confirmed by JC):** S3 keys, Resend key, SMTP credentials, the file key, the backup passphrase and the map provider key live in a `.env` file (mode 600) or Docker secrets (`*_FILE`), never in the database or Admin page. Admin page shows read-only status, test buttons and the migrate action. Non-secret settings (notification defaults, send time, time zone, backup schedule and retention, the update-check toggle) are editable in Admin. **The identity-number encryption key (`IDENTIFIER_ENCRYPTION_KEY`, decided Nov 16, see `kinship-identity-numbers.md`) is a secret of this kind and is not in backups.**
- **Backups (JC asked, Nov 14):** built in, no extra container. `BACKUP_ENABLED`, `BACKUP_DEST` (`local` or `s3`), `BACKUP_PASSPHRASE`. One encrypted archive of the Postgres dump plus media files. Admin → Backups (SuperAdmin) has Back up now, Test the latest backup, a list with Download and Restore, and the command line. **Restore from the app is built (0.3.0 step 36, ADR 0031):** two steps (a check, then a single-use ticket, the typed word RESTORE and the password), a safety copy first, a maintenance page while it runs, the api restarts when it ends; only listed archives; a backup that carries photos restores them too (0.3.0 step 37, ADR 0035: the key is checked first, the photos are verified and swapped in after the database commit); accounts deleted or disabled since the backup come back active with the backup's passwords. The backup does **not** include the file key, the identity-number key or the passphrase, which the deployer must store separately. See `kinship-research-records-and-backup.md`. The automatic safety copy before a migration is separate from these backups (see the update notice above).
- Notifications: birthdays (lead time: on the day, 1 day, 1 week; email and/or in-app bell), optional anniversaries, remembrance days, weekly digest (off by default), and "an admin edited my medical record". Per-user settings with SuperAdmin defaults. **Children under 18 are excluded from birthday reminders (confirmed).** A daily in-app job sends them; no separate scheduler container. The SuperAdmin's bell also carries the update notice (in-app only).

Admins see five header tabs: Home, Family tree (Chart, Relationship finder), Media, Archive (Timeline & map, **Sources, Places, Stories**, Reports), Health and DNA. Members and Users see the first four. **Health and DNA live on each person's profile** (tabs Medical history and DNA); the Health and DNA header tab is an admin-only overview. The profile tabs are Facts, Events, Stories, Photos & documents, Medical history and DNA. The chart's view switcher is one icon at the top right that expands to icon-only options (built). Account menu (avatar pill) holds My profile, My settings, Import & export, Admin (admins only), Deployment, **About KinShip**, Sign out. The person panel sits left of the tree and collapses to a rail. Home → Jump to has **Health history for my doctor**. Admin tabs: Users, Roles & access, Sign-in & SSO, Storage & email, Backups, **Updates**, Duplicates, Emails, Languages.

**Add relative (redesigned Nov 14 from JC's MyHeritage screenshots):** a diagram of the selected person with their parents, partners, siblings and children as cards, each with a "+" to add that kind of relative, then a short form. Two layouts: a person with parents on the tree, and a person with none. Details in `kinship-navigation.md`.

**A spouse's family (decided by JC, Nov 14):** one tree. An in-law's own parents are hidden in the main chart and opened with a small logo-green leaf on the in-law's card, which flips the chart to that family; there is no back button because both views are full charts. Details in `kinship-tree-views-and-dna.md`.

## Roles and edit scope (names changeable, access levels fixed)
- SuperAdmin, Family Admin, Member, User. Baseline User sees all public tree data and profile photos. **With single sign-on, a provider group can set SuperAdmin, Family Admin, Member or User, and a person in no mapped group gets User (decided by JC, Nov 18). SuperAdmin by group needs a local break-glass password and a local authenticator-app (TOTP) login, which ships in 0.4 (decided by JC, Nov 18). There can be more than one SuperAdmin, and the last SuperAdmin can never be demoted. While single sign-on is on, local sign-in is off for every role; setting `OIDC_ENABLED=false` in `.env` and restarting is the only way back (decided by JC, Nov 18).** See `kinship-sso-oidc.md`.
- **Admins edit everything on the tree.** **Members can edit only their own profile** (their facts, their own relationships, their own photo). Users cannot edit the tree. In the mockup, other people's edit buttons are disabled for a Member with the tooltip "You can only edit your own profile".
- **Members can add descendants only (decided by JC, Nov 14):** on their own profile they can add children (and through them grandchildren). They cannot add parents, partners, siblings or custom-label relatives; for those they ask an admin. In the mockup a Member's Add relative dialog offers only "Child" with a note saying so. Choosing the child's other parent from existing partners or "not on the tree" still works.
- **Members can add sources (decided by JC, Nov 15):** to the Sources library and as citations and files on any person's facts (they still cannot change the fact itself). Admins and Members can also add places and stories; Users can only read.
- Every account can edit the medical record of its own linked person, whatever its role.
- Custom conditions, cancer types **and procedures** (shared lists): merging and renaming is an **admin** task. Merging duplicate people and places is also an admin task.
- **Update notices and the update-check settings are for the SuperAdmin only. The "What's new" popup after an update is shown to every admin (SuperAdmin and Family Admins).**
- **Account administration (built in 0.3.0 step 35, Nov 21; ADR 0029; Admin → Users row menu).** A SuperAdmin changes the role of any other Family Admin, Member or User account (to any of those three). A Family Admin switches Member and User accounts between Member and User only and never makes a Family Admin. A role change never makes a SuperAdmin (there is no promote action, ADR 0012 stands) and takes effect on the account's next request, with no sign-out. A SuperAdmin disables, enables or deletes any other account; a Family Admin only Member and User accounts. **A disabled account** is signed out at once, cannot sign in (the answer is the same as for a wrong password), keeps its person link and history, and its old password works again when it is enabled (the message says so). **Delete** needs the account disabled first and its email typed; it removes the account only, never the person or their record, and removes the accepted-invitation rows that hold the email. **Nobody acts on their own account, and the last active SuperAdmin can never be demoted, disabled or deleted, by any route.** Invitations made by an admin who is later disabled or deleted stay valid (each has its own Revoke).

## Medical visibility (private by default, shared person by person)
- **Decided by JC (Nov 14):** health information is private. A living person's record is visible only to that person until they **share it with specific individuals** (people who have accounts). There is no "all family accounts" or role-wide option any more. **Admins have no special access:** an admin sees a record only if that person shared it with them (or the person is deceased). Role does not matter; sharing is per person.
- After death every record becomes visible to all accounts. **A deceased person's cause of death (a field on the death fact) is visible to every account.**
- Conditions marked Private stay visible only to the person while living (sharing does not reveal them, even to the people chosen). After death they are visible.
- **Surgeries and procedures (added Nov 15) follow exactly the same rules as conditions:** part of the same record, shared with it, can be marked Private, visible to all after death, same row-level security policies, same change history and admin-edit email. They are deliberately **not** an Events type, because events are visible to every account. Files attached to a surgery follow the record's visibility. See `kinship-surgeries-and-procedures.md`.
- Admins can edit another person's record only when it is visible to them (shared with them, or the person is deceased); every edit is written to the change history and the person is notified.
- Reports, the patterns lists, the medical patterns report and the family health history report count only records, conditions and surgeries the viewer can already see, and say how many relatives were left out because they are not shared or have no record.
- The mockup has checkboxes under "Who can see my record" listing the other people with accounts. Sharing and un-sharing are written to the change history.
- **Shares and access are keyed by person, never by account (rule from ADR 0029, Nov 21).** A share, and every access check for health records and identity numbers, names the people involved and resolves the viewer through `users.person_id` at read time. Deleting or unlinking an account then loses no sharing choice and exposes nothing, and a new account linked to the same person gets back exactly what that person had. **Open risk, a 0.6 blocker (issue #183):** an admin can link a new account to a living person who has no account, and from 0.6 that would give the account's controller the person's whole private record. The 0.6 phase 1 decides what linking is allowed (the lean: refuse when the person has a non-empty private record).

## DNA visibility (decided by JC, Nov 14)
DNA results (tests, haplogroups, ethnicity estimate) are **visible to every account, living or deceased**. There is no sharing choice. Match lists and raw files stay private to the tested person (assumption: JC did not say otherwise, and they name living people who never joined KinShip). Admin upload on someone's behalf still needs a permission checkbox. Details in `kinship-tree-views-and-dna.md`. In the release plan the DNA tab ships in 1.2 and match lists in 1.3.

## Identity numbers (asked by JC, Nov 16; full spec in `kinship-identity-numbers.md`; built in the mockup Nov 16)
- **What:** a person can carry one or more national or civil identity numbers, for example the **Cédula** (Dominican Republic) or the **CURP** (Mexico). The main use is **deceased relatives**, where the number helps when requesting records from the state. Shown in an **Identity numbers** section on the profile Facts tab and edited in Edit details.
- **Each entry:** country, type (seeded list per country plus a custom label that joins a shared list), number, optional issued and expiry dates, issuing place, note, and a Sources & files panel (for a scan of the card or a registry record). Record numbers of birth, marriage and death certificates are **not** identity numbers: they go in the page or record number of the citation on that fact (decided Nov 16). Format hints give soft warnings only and never block saving.
- **Starter list (decided by JC, Nov 16):** United States, Mexico, Dominican Republic, Canada and 2 to 3 European countries. My proposal for the types and the European picks (Spain, Italy, United Kingdom) is in the identity doc; JC may swap the European countries.
- **Visibility:**
  - **Deceased person (decided by JC, Nov 16):** visible to their **parents, siblings and children, and their legally married spouse**, with accounts, **and to admins**. **Half and adopted siblings, and adoptive parents and children, count** (decided Nov 16; adoption needs a small parent/child link, previously paused). Not shown to other Members or Users.
  - **Legally married spouse (decided by JC, Nov 16): spouse only, never an unmarried partner.** A relationship counts when its status is **Married or Widowed**; **Separated also counts (decided Nov 16: still legally married).** No confirmation is asked when a status changes. Partner, Engaged, Friends, Unknown, Other, Divorced and Annulment do not count. The existing relationship status decides it, so the rule is only as good as the status.
  - Step relatives, in-laws and grandchildren do not count.
  - **Living person *(assumption)*:** visible only to that person (admins have no special access) and to anyone they share with.
  - **Who edits (decided Nov 16):** the person themself while living (admins cannot); after death an admin or next of kin (the same people who can see the numbers).
- **Protection:** **field-level encryption in v1.0 (decided, my recommendation accepted)** with its own secret key that is not in backups; masked with a logged Reveal and Copy button; enforced by row-level security like medical data; never in emails, the tree, search, URLs or logs; GEDCOM export leaves them out unless the box is ticked.
- **Records request sheet (decided by JC, Nov 16):** a printable letter and fact sheet for requesting a **deceased** relative's records from a state or other office. Fixed template, no AI; English or Spanish; shows only what the viewer may see; lists identity numbers (each with its own checkbox), names and birth and death facts, parents, attached sources, the records wanted, and the requester's relationship from the relationship finder. Print, PDF, text and Copy as text. Listed under Reports. A legally married spouse can make it; an unmarried partner cannot see the numbers and so gets a sheet without them.
- Proposed to ship with release 0.6, next to medical history and sharing, because it reuses that work.

## Sources, places, events and stories (decided by JC, Nov 14; see `kinship-research-records-and-backup.md`)
- **Sources on any fact, like MyHeritage.** Birth, death and cause of death in Edit details each have a Sources & files panel (pick a library source or name a new one, page or record number, reliability, link, file). The profile shows each fact with citations, file chips and a "+ Source or file" button. Reliability: Primary, Secondary, Questionable.
- **Cause of death** is a field under the death date and place, with its own sources and files.
- **More event types** (occupation, residence, education, military, immigration, emigration, naturalization, baptism, burial, census, award, religion, custom label) with date, place, details, sources and files. Health events are not event types; they go in Medical history.
- **Sources library** (Archive → Sources, with Repositories) and **Places library** (Archive → Places: kind, part of, coordinates, other names, duplicate merge). **Stories** (story, note, recording, research note; admins-only option) on the Archive → Stories page and each profile.
- **Duplicate merge** (Admin → Duplicates): fixed-rule suggestions, field-by-field choice, blocked when one record is living and the other deceased, medical records never merged, never automatic, **undo for 30 days (decided by JC, Nov 15)**.

## Relationship finder
**Built in 0.3.0 step 34 (Nov 21; ADR 0028; page at `/relationship?a=&b=`, endpoint `GET /api/relationship`).** Where the built finder differs from the list below, this paragraph wins: the picker searches names only (no year or place); there is no "With birth places" Details switch (no place data until 0.5) and no Print or Download PDF buttons (printing and PDF come with the reports in 0.7); only Married and Widowed give in-law and step names (the same rule as the profile, ADR 0010; Separated does not either, so a divorced, annulled or separated partner of a blood relative reads "Father's ex-wife", or "ex-partner" when no gendered word applies; Separated read "separated wife" until step 35, #180); a single shared ancestor is "half" only when a side has a second, different known parent below it, otherwise the plain name; a spouse's grandchild reads "Step-grandson"; one marriage hop at most; the closest relationship is the headline and up to three others show as "Also related as"; an admin's custom label shows as "Also called ..." and replaces only a derived step headline; the finder follows the viewer's lineage view and, when only the other view connects two people, says so. Original list:
- Pick any two people with a searchable picker (type a name, year or place; arrow keys and Enter work). Swap button. Shows "<B>'s relationship to <A>" plus a diagram of the path, with the shared ancestor(s) at the top and each person's line down to them. Details switch: Basic or with birth places. Quick example pairs in the mockup.
- Names are worked out from the tree only: find the closest shared ancestor, count generations up from each person (dA, dB). Direct line gives parent, grandparent, great-grandchild and so on. dA=dB=1 is sibling; dA=1 with dB>=2 is niece/nephew (grand, great-grand...); dB=1 with dA>=2 is aunt/uncle (great-...). Both >=2 is cousin: level = smaller count minus 1 (first, second, third...), "removed" = difference between the counts (once, twice...).
- Half: a single shared ancestor gives half (Half-brother, Half-aunt, Half first cousin once removed); a shared ancestor couple gives full.
- Marriage links give in-law and step names (Sister-in-law, Father-in-law, Daughter-in-law, Stepbrother, Stepmother, Step-grandmother, Wife's nephew, Stepbrother's son). Current marriages (Married and Widowed) count. **(The mockup also counted Separated; the built finder does not. See the paragraph above.)**
- **Divorce (decided):** a divorce does not create or keep in-law names. A former partner of a blood relative is described plainly ("Father's ex-wife"). Descendants still find the person through blood: Leo finds Elena as Grandmother after her divorce from Daniel. A current spouse of a grandparent is Step-grandparent. Annulment and Separated partners are described the same way as divorced ones (built, step 35).
- A "What 'once removed' means" side panel appears for removed cousins (added in another session): shows each person's generation count below the shared ancestor, how the cousin number and the removed number are worked out, and that the term reads the same from either side.
- Generation note, list of closest common ancestors, Print and Download PDF buttons (**Print and PDF not built in 0.3.0**).

## Reports (no AI)
- **Life summary** for any person, living or deceased: Early life (birth, parents, siblings with relationship names), Family (each marriage with date, place, how it ended, children together, children with someone else), Death and family left behind (age, survivors: spouse, children, grandchildren, great-grandchildren). Optional sections: health history on record (conditions **and surgeries and procedures**, only if the viewer may see that record; cause of death shown separately), life events list, citations and sources as numbered footnotes with links.
- Living children (under 18) get only name, birth year and parents. Living people's private conditions and surgeries are visible only to that person.
- **Family health history (added Nov 15, for a doctor visit):** a one-page summary of the questions a PCP asks. Checklist (heart disease, blood pressure, cholesterol, diabetes, stroke, cancer by type, osteoporosis, thyroid, dementia, mental health) with which relative and the age at diagnosis, then tables for parents, brothers and sisters, children and optionally grandparents, aunts and uncles (age or age at death, conditions with age at diagnosis, cause of death). **Own surgeries and procedures are listed with own conditions (on by default); relatives' surgeries are an optional column, off by default (added Nov 15, my assumption).** Names off by default; "unknown" is never shown as "none"; private conditions and surgeries of living relatives never appear; own conditions optional; can be made for a child; Copy as text. Details in `kinship-family-health-history-report.md`.
- **Records request sheet (added Nov 16, for a state or office records request about a deceased relative; built in the mockup):** see Identity numbers above and `kinship-identity-numbers.md`. Deceased people only; identity numbers appear only if the viewer may see them (parent, sibling, child, legally married spouse or admin); English or Spanish; the one report that lists identity numbers by default.
- **Medical patterns** for a person: conditions that repeat among their blood relatives (in-laws and step relatives left out), with relationship, cancer type and since-year, a count, a flag when the person has it too, and a note on how many relatives were left out (not shared, or no record). States that it is family history, not a risk calculation or medical advice. Conditions only; surgeries are not analyzed.
- **Family group sheet (added at JC's request, Nov 14):** the standard one-page genealogy record for a couple. Pick a person and, when they have several relationships, which one. Shows the husband and wife (born, place, died, father, mother), the marriage or relationship (status, date, place, end date) and a table of the couple's children in birth order (name, sex, born, place, died, spouse). Living children under 18 show name, sex and birth year only. A person with no relationship gets a message instead. In the mockup the husband and wife labels follow gender, and sources are not yet listed on the sheet.
- **Family book**: printable book for the descendants of a chosen person (plus spouses): cover page, contents, one chapter per person (the life summary, one page each when printed) and an index of names. Options: life events, health histories (off by default, and only what the viewer can see), sources. (Ships in 1.1.)
- **Descendants** outline with spouses, **Ancestors** by generation with relationship names, **Data check** (missing places, events without sources, branches with no parents).
- Output: print or save as PDF, Word (.docx), plain text. Person picker is searchable. (Print, PDF and text in 1.0; Word in 1.1.)
- Idea not yet in the mockup: birthday and anniversary list.

## Partner relationships
- Status list (fixed, from JC's reference screenshot): Married, Divorced, Separated, Widowed, Engaged, Partner, Friends, Annulment, Unknown, Other.
- **Legally married (defined Nov 16, for identity-number access):** a relationship is a legal marriage when its status is **Married, Widowed** or **Separated**. **Partner, Engaged, Friends, Unknown, Other, Divorced and Annulment are not.** Separated was confirmed by JC on Nov 16. Nothing else in the app changes because of this; it only decides who sees a deceased person's identity numbers and the sheet.
- Each relationship has: status, marriage date (precision Exactly/About/Before/After), marriage place, and an end date shown only for Divorced (divorce date), Separated (separation date) and Annulment (annulment date).
- A person can have several relationships over time. Changing a status never removes children.
- **Unmarried parents:** when a child has two parents who are not linked yet, the app creates a relationship for them with status **Unknown** (not Partner). The Add relative dialog says so.
- Labels follow status and gender (Wife, Ex-wife, Wife (separated), Fiancée, Wife (widow), Late wife and so on). Derived relatives: step-parents and stepchildren (through a Married or Widowed relationship), half-siblings.
- **Widowed is automatic.** Marking a person deceased (Edit details, status Deceased) sets their Married relationships to Widowed and shows a toast saying their medical history is now visible to every account. Marking them living again reverts only the ones set automatically. If a marriage ended earlier, an admin changes the status by hand (for example Divorced), and that manual choice is kept. **Widowed draws like Married (solid line)** because the deceased marker already shows the spouse has died.
- **Children hang from the relationship.** A child with both parents on the tree is drawn from the midpoint of that couple's line, so kids from a previous relationship stay with that union. A child with only one parent on the tree is drawn from that parent alone. Add relative asks for the other parent: a partner on the tree, or "not on the tree".
- Profile shows a card per relationship with dates, place, children together, the partner's children from another relationship (labelled "with <other parent>" or "other parent not on the tree", and "your stepson/stepdaughter" when married), and what each person did afterwards.
- **Tree line convention (no letter badges):** solid line = together (Married, Engaged, Partner, Widowed). Dotted line = ended or not a marriage (Divorced, Separated, Annulment, Friends, Unknown, Other). Clicking a couple line opens that relationship to edit (if the role may); hover shows the status.

## Names, dates and photos (added in other sessions)
- **Maiden and married surnames.** People have a birth (maiden) surname and an optional married surname. Fields appear when a relationship is Married (Add relative, first-run setup, Edit details). **Built in 0.3.0 step 28 (ADR 0024):** a per-user setting in My settings, Names (and the chart's gear) picks one of four forms: Maiden name (Married name) (the default), Married name (born Maiden name), Married name, or Maiden name; prefix and suffix have on/off switches; people also have an optional nickname and surname particle. Both surnames stay on the profile under Facts.
- **Dates.** Entered as YYYY, YYYY-MM or YYYY-MM-DD with a live preview and validation. **A calendar picker (built in 0.3.0 step 36, ADR 0032) sits next to the typed field, which stays primary; it writes the same three forms. Each user chooses the first day of the week in My settings, Display: Sunday (default), Monday or Saturday.** Display format is a per-user setting in My settings (Jan 1, 2026; 1 Jan, 2026; 1 Jan 2026; January 1, 2026; 2026-01-01; 01/01/2026; 01/01/2026 day first). The tree, profile, birthday list and reports follow it.
- **Profile photos.** Any role that may edit a person can upload a photo from their profile (**built in 0.3.0 step 37**: the Photos card on the profile, with Set as profile photo, Remove from this person and Delete; admins, and a Member for their own person and people in their line; a User never). Photos of living people are visible to every signed-in account. The photo shows as the avatar on the tree node, relationship cards, lists and search results (the medical page comes with 0.6). **Pictures only (JPEG, PNG, WebP) in 0.3.0**; the server re-encodes every upload and keeps no EXIF except the date taken, which the uploader sees and can edit (GPS is always dropped); documents and PDFs come later. The Media tab (`/media`, built in step 37e) is a family-wide grid of photos for every role with a person filter and "Load more"; it has no upload, titles or captions in 0.3.0. "Set as profile photo" from Media also works.
- **First-run setup wizard** (seven steps with progress bar): Account (SuperAdmin name, email, password), Tree (name, like "Hale Family", and the color scheme swatches), You (given name, surname, birth date, gender), Partner (relationship status, birth surname, optional married surname), Parents (father, mother, living or deceased), Children (several rows, choose the other parent for each, or "not on the tree"), Review (preview of the people created, and a "Check for new versions" switch, on by default, which is the same switch as Admin → Updates; the earlier paragraph about the daily update check was replaced by it in step 37). The screen never appears once an account exists.

## Medical history (self-service)
- Every account can edit the medical record of its own linked person (blood type, conditions with since-year, status, optional source URL, **and surgeries and procedures**). It appears on the person's profile in the **Medical history** tab.
- Statuses: Active, Managed, Monitored, In remission, Resolved.
- Conditions are chosen from a searchable list of common conditions (about 70, grouped by category, matches on common names such as "high blood pressure"). If nothing matches, the user types a new name and adds it; custom conditions join the family list for everyone. Admins can merge duplicates later. Conditions already on the person's record are shown as unavailable.
- **Cancer is one condition with a required type.** Choosing Cancer reveals a "Type of cancer" searchable field (about 24 common types such as Breast, Prostate, Lung, Colorectal, Skin (melanoma), Leukemia, Lymphoma, plus Unknown type). If the type isn't listed, the user types it and adds it as a new type, which joins the shared list. A person may have several cancer entries. Shown as "Cancer · Breast"; family patterns list "Name (breast)".
- **Surgeries and procedures (added Nov 15; full spec in `kinship-surgeries-and-procedures.md`; not in the mockup yet):** a second section on the Medical history tab, under the conditions. Each entry has a procedure (required, from a searchable list of about 45 common ones such as appendectomy, knee replacement, cesarean section, mastectomy, bypass; a new name can be typed and joins the shared list, admins merge), an optional flexible date (age at the time is worked out), an optional **related condition** from the person's own record (Cancer · Breast → Mastectomy), an optional place from the Places library, notes, an optional source URL and a Private checkbox. The same procedure can be added more than once. Scope: operations and invasive procedures a doctor asks about, not routine tests or vaccines.
- Sharing: **private by default; share with specific people** (see Medical visibility above).

## Tree views and DNA (see `kinship-tree-views-and-dna.md`)
Four chart views (Family tree, Pedigree, Fan, Descendants). DNA results from third-party providers, several per person, uploaded by the person or by an admin on their behalf, visible to every account, with a tree check of matches (own page only), Y-DNA and mtDNA lines, and an orange tree badge for everyone with an upload.
